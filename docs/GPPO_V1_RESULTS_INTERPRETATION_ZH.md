# GPPO-v1 实验结果解读

本文档解释 `GPPO无偏好` 分支中每张结果图表达的含义、可以支持的结论，以及不能据此过度推断的内容。

## 1. 应该怎样阅读这些图

四类图分别回答四个问题：

1. **Makespan 图：**完成整个任务集合需要多长时间？
2. **完成率图：**较短的 makespan 是否以留下未完成任务为代价？
3. **运行诊断图：**通信、无效动作和失效任务重分配是否正常？
4. **训练曲线：**100 updates 后是否基本收敛，结果是否稳定？

不能只选择其中一张图下结论。尤其是 makespan 必须与完成率一起解释。

## 2. Makespan 多方法对比

![四种方法的多尺度 makespan 与 95% 置信区间](../assets/readme/benchmark_makespan.png)

### 2.1 指标定义

Makespan 是所有活动任务预计完成时间的最大值：

```text
M = max(C_i)
```

数值越小，代表整个任务集合越早结束。横轴 `2x8` 至 `6x36` 分别表示 UAV 数量和初始任务数量。误差棒表示 95% 置信区间。

### 2.2 GPPO 相对 PPO

| 规模 | GPPO | PPO | GPPO - PPO | 解释 |
| --- | ---: | ---: | ---: | --- |
| `2x8` | 7.002 | 6.906 | +0.096 | GPPO 略差 |
| `3x12` | 6.920 | 7.471 | -0.551 | GPPO 更好 |
| `4x20` | 9.217 | 10.282 | -1.064 | GPPO 更好 |
| `5x28` | 10.363 | 11.543 | -1.179 | GPPO 更好 |
| `6x36` | 11.046 | 12.518 | -1.472 | GPPO 更好 |

`GPPO - PPO` 为负表示 GPPO 的 makespan 更短。GPPO 在 5 个规模中的 4 个优于 PPO，而且规模增大后优势总体扩大。

**这表达的核心含义：**简单小规模问题不一定需要复杂图策略；当 UAV、任务依赖和动态事件增多时，图结构与事件同步开始体现价值。

### 2.3 GPPO 相对 EEC Greedy

| 规模 | GPPO - Greedy | 解释 |
| --- | ---: | --- |
| `2x8` | +0.171 ± 0.056 | GPPO 显著更差 |
| `3x12` | +0.035 ± 0.118 | 基本持平 |
| `4x20` | -0.411 ± 0.151 | GPPO 更好 |
| `5x28` | -0.206 ± 0.263 | 均值更好，但不显著 |
| `6x36` | -0.293 ± 0.245 | GPPO 更好 |

**这表达的核心含义：**GPPO 没有在所有规模上超过强贪心。小规模下，直接选择“预计最早完成”的局部规则已经很有效；复杂规模下，GPPO 才更可能利用全局图关系。`2x8` 的负结果必须保留。

### 2.4 为什么不能单看 makespan

如果一个方法只完成一半任务就结束，它的 makespan 可能看起来并不长。因此 makespan 只有在完成率相近时才能直接比较。PPO 在大规模上存在大量未完成任务，所以必须结合下一张图。

## 3. 任务完成率

![四种方法的多尺度任务完成率](../assets/readme/benchmark_completion_rate.png)

完成率定义为：

```text
completion_rate = 完成任务数 / 需要完成的全部任务数
```

GPPO、Random 和 Greedy 在本协议中基本达到 100%。PPO 的完成率则随规模下降：

| 规模 | PPO 完成率 |
| --- | ---: |
| `2x8` | 约 83.0% |
| `3x12` | 约 79.0% |
| `4x20` | 约 60.8% |
| `5x28` | 约 60.5% |
| `6x36` | 约 54.7% |

**这表达的核心含义：**GPPO 相对 PPO 的优势并不是“少做任务所以结束更快”，而是在完成更多任务的同时保持较短 makespan。尤其在 `6x36`，GPPO 完成率为 100%，PPO 约为 54.7%，但 GPPO 的 makespan 仍更低。

最终完成数偶尔超过初始任务数，例如 `2x8` 平均完成数为 8.264，是因为 episode 中可能触发新任务事件，并非统计错误。

## 4. Event-GPPO 运行诊断

![Event-GPPO 通信、无效动作和重分配诊断](../assets/readme/gppo_diagnostics.png)

### 4.1 通信事件

| 规模 | 平均通信事件数 |
| --- | ---: |
| `2x8` | 1.060 |
| `3x12` | 1.546 |
| `4x20` | 3.370 |
| `5x28` | 3.998 |
| `6x36` | 5.430 |

规模越大，episode 越长，天气变化、失效、新任务等事件出现的机会越多，因此同步次数增加是合理的。

**这表达的核心含义：**事件模式没有在每个决策步都同步，而是只在关键事件发生后更新缓存，通信次数受到控制。

当前“通信一次”表示一次状态同步事件，不等于真实字节数、带宽、延迟或丢包率，因此不能宣称已经节省了某个百分比的真实无线带宽。

### 4.2 无效动作

| 规模 | GPPO 无效动作数 |
| --- | ---: |
| `2x8` | 2.826 |
| `3x12` | 3.142 |
| `4x20` | 11.622 |
| `5x28` | 14.126 |
| `6x36` | 18.296 |

环境维护两套状态：

```text
truth  = 真实物理状态
belief = 策略根据最近通信得到的缓存状态
```

例如 belief 认为 UAV 仍存活，但 truth 中该 UAV 已失效，策略根据旧缓存分配任务时就会产生一次无效动作。

**这表达的核心含义：**弱通信缓存确实造成了状态不一致，而且规模越大越严重。训练过程中无效动作没有持续恶化，但绝对数量仍偏高，因此这是后续改进重点，而不是已经解决的问题。

可考虑加入 belief age、状态时间戳、合法性预测头、不确定性动作掩码和失效后的局部即时刷新。

### 4.3 重分配成功率

| 规模 | 重分配成功率 |
| --- | ---: |
| `2x8` | 100% |
| `3x12` | 100% |
| `4x20` | 100% |
| `5x28` | 约 94.8% |
| `6x36` | 约 98.6% |

正在执行任务的 UAV 失效后，任务会重新回到待分配状态；其他 UAV 接管并完成后，记为一次成功重分配。

**这表达的核心含义：**当前环境中的失效恢复链路总体有效，但小规模失效样本较少，100% 不代表已经得到充分统计证明。应同时报告重分配事件总数和条件成功率。

## 5. Validation 收敛曲线

![GPPO 与 PPO 的验证曲线](../assets/readme/validation_curves.png)

### 5.1 Makespan 是否收敛

GPPO 的 validation makespan 在早期下降，约 40～60 updates 后进入平台区，60～100 updates 之间主要是小幅波动。后期相对变化约为 `-0.49% ± 1.77%`，其 95% 置信区间包含 0。

**这表达的核心含义：**继续训练没有表现出稳定、明显的改善，因此可以称为“基本收敛”；但不能声称每个种子都严格完全收敛。

### 5.2 Completion rate

GPPO 在训练中后期保持约 1.0，PPO 约在 0.60～0.63。这说明 GPPO 的完成率优势不是某一个偶然 checkpoint 产生的。

### 5.3 Invalid actions

GPPO 的 validation invalid actions 大约稳定在 12～13，没有随 update 持续上升；PPO 大约在 118～121。

**这表达的核心含义：**GPPO 没有通过不断增加非法选择来换取 makespan 改善，图结构和事件同步显著减少了基于旧状态作出的错误分配。不过 12～13 仍不是理想值。

### 5.4 Communication events

GPPO 的通信次数大约稳定在每 episode 3.7～3.9 次，没有随训练不断增加。

**这表达的核心含义：**性能改善没有伴随越来越多的状态同步。但通信主要由环境事件规则触发，不能把该曲线全部解释成 actor 自主学到的通信策略。

### 5.5 Checkpoint 选择

五个 GPPO 种子的 validation-selected checkpoint 为：

```text
seed 1 -> update 100
seed 2 -> update 50
seed 3 -> update 80
seed 4 -> update 40
seed 5 -> update 60
```

大部分种子在 40～80 updates 进入稳定区域，但 seed 1 的最佳 checkpoint 位于 update 100。这也是使用“基本收敛”而不是“完全收敛”的原因。

### 5.6 两种重分配数值为何不同

Validation 曲线中约 0.3 的量通常表示“每 episode 成功重分配数量”；诊断图中 95%～100% 表示在实际发生待重分配任务的条件下，最终恢复成功的比例。二者分母不同，并不矛盾。

训练曲线来自随机 rollout，会受到轮换规模、随机事件和随机动作采样影响，因此更抖动。Validation 使用固定场景和固定种子，更适合判断收敛。正式结论应以 validation 为主，训练曲线用于排查 actor loss 爆炸、完成率崩塌或通信异常漂移。

## 7. 最终可以得出的结论

这些结果共同支持：

1. GPPO 在 5 个规模中的 4 个相对 PPO 保持 makespan 优势；
2. GPPO 在完成更多任务的同时保持较短 makespan；
3. 增加到 `100 updates × 16 episodes` 后，多数规模优势没有反转；
4. 训练中后期基本进入平台区；
5. 通信次数有限且没有随训练持续增加；
6. 失效重分配机制总体有效；
7. 无效动作没有随训练恶化，但仍随任务规模明显增加；
8. GPPO 没有在所有规模上超过 EEC Greedy，`2x8` 是明确负结果。

因此，当前最准确的阶段判断是：

> GPPO-v1 已通过结构级稳定性复核，可以作为后续 PCRL 改造的固定工程基线；但它不是原论文数值级完整复现，也不能证明 GPPO 在所有规模上都优于强贪心。

## 8. 不能从这些图推出什么

当前结果不能证明：

- 已复现原论文绝对数值；
- GPPO 在所有规模上优于 Greedy；
- 全部增益单独来自 GNN；
- 已彻底解决弱通信下的无效动作；
- 通信次数等价于真实网络带宽；
- 100 updates 后所有种子都严格完全收敛。

一句话概括四类图：

> Makespan 看“快不快”，完成率看“是否真的做完”，运行诊断看“系统是否健康”，训练曲线看“结论是否收敛且可重复”。
